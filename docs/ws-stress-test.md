# WebSocket 생명주기 스트레스 테스트 — 1차 실측

> 실행: 2026-09-01 · 대상 브랜치: `kimdoyoung/ws-jvm-memory-limit` (브로커 하드닝 적용 후)
> 설계: `docs/sprint4-architecture-review.md` §6 · 검증 대상 설정: 같은 문서 §3
> 하네스: `backend/src/test/java/com/memorin/global/config/WebSocketLifecycleStressTest.java`

게이트 문구는 "탭 닫기 시 InMemory 세션 즉각 반환"이다. 이걸 숫자로 확인한 기록이다.

```bash
JWT_SECRET=... ./gradlew stressTest
```

CI에서는 돌지 않는다(`@Tag("stress")` → `test` 태스크에서 제외). 하트비트 주기만큼 기다리는 구간이 있어
전체 실행에 약 1분 걸린다.

## 실행 환경

| 항목 | 값 |
|---|---|
| 테스트 JVM 힙 | 512MB 고정 (`stressTest` 태스크) — 누수가 늦게 드러나지 않도록 |
| DB | Testcontainers PostgreSQL 18 (운영과 동일하게 Flyway로 스키마 생성) |
| 서버·클라이언트 | **같은 JVM** (`@SpringBootTest(webEnvironment = RANDOM_PORT)`) |
| 브로커 설정 | 하트비트 10초/10초, sendTimeLimit 10초, 버퍼 512KB, 프레임 64KB |

## 결과

| 측정 | 합격 기준(§6 초안) | 실측 | 판정 |
|---|---|---|---|
| 세션 정상 반환 | 0으로 복귀 | 50세션 DISCONNECT → **101ms** (3회: 105/103/101) | ✅ |
| 비정상 종료(RST) 회수 | 하트비트 2~3주기 내 | 20세션 RST → **103ms** (104/103/105) | ✅ 주기와 무관하게 즉시 |
| **무응답(블랙홀) 회수** | 하트비트 2~3주기 내(20~30초) | 10세션 → **35.1초** (36.8/36.9/35.1) | ⚠️ 기준 초과 — 아래 §발견 1 |
| 힙 증가 | 초기값 대비 증가 없음 | 연결·해제 100회 → 66MB → 66MB (**Δ 0MB**) | ✅ |
| 브로드캐스트 지연 | 실측 후 기준 확정 | 구독자 30 × 200건 → **p95 106ms** (98/106) | 기준 후보: p95 < 300ms |
| 느린 수신자 격리 | 다른 클라이언트에 영향 없음 | 정상 3명 **183/180 전부 수신**, 멎은 세션만 종료 | ✅ |

## 발견 1 — 무응답 세션 회수는 "하트비트 × 3 + 태스크 주기"다

초안의 "2~3주기"는 틀렸다. Spring은 하트비트 값을 그대로 쓰지 않고 **3을 곱해서** 읽기 타임아웃을 잡는다.

`SimpleBrokerMessageHandler$SessionInfo`의 바이트코드에서 확인했다:

```
private static final long HEARTBEAT_MULTIPLIER;   // = 3
readInterval = max(클라이언트 송신 주기, 서버 수신 주기) * 3
```

10초 설정 → 읽기 타임아웃 30초 + 하트비트 태스크 주기(≈5~7초) = **35~37초**. 실측과 일치한다.

교차 검증으로 양쪽을 5초/5초로 낮춰 다시 측정했다 → **17.0초**. 배수 관계가 그대로 재현된다.

**그럼에도 10초를 유지한다.** 협상값이 `max(클라이언트, 서버)`라서, 서버만 5초로 낮춰봐야
브라우저 stomp.js 기본값(10초)과 만나면 다시 30초가 된다. 절반으로 줄이려면 **FE도 5초로 맞춰야** 하고,
그 대가로 얻는 것은 "네트워크가 끊긴 세션이 35초 대신 17초 만에 회수"다.
탭 종료·프로세스 kill은 RST로 0.1초 안에 회수되므로(위 표 2행), 게이트가 말하는 "탭 닫기"는 이미 충족한다.

→ **기준 문구를 `하트비트 × 3 + 태스크 주기`로 고친다.** 값 변경은 FE 협의 사항으로 남긴다.

## 발견 2 — 격리는 설계대로 동작한다

수신이 멎은 클라이언트 1명 + 정상 3명에게 32KB × 60건(1.9MB)을 뿌렸다.

- 멎은 세션만 전송 상한에 걸려 서버가 정리했다 (`1 send limit`, `1 closed abnormally`)
- 정상 구독자는 **전량 수신**했고 지연도 늘지 않았다

§3에서 넣은 `setSendBufferSizeLimit(512KB)` / `setSendTimeLimit(10초)`가 실제로 한 세션을 격리한다는
확인이다. 이 설정이 없으면 밀린 메시지가 힙에 그대로 쌓인다.

## 하네스의 한계 (숫자 해석 시 주의)

1. **서버와 클라이언트가 같은 JVM이다.** 세션 수·힙을 직접 읽으려고 택한 구조라, 절대 처리량은
   서버 한계가 아니라 **테스트 클라이언트의 한계**다. 실제로 구독자를 11명으로 올리자 정상 세션까지
   전송 상한에 걸렸다 — 서버가 아니라 클라이언트가 못 따라간 것이다. 그래서 격리 시나리오는 3명으로 줄였다.
2. **JSR-356 클라이언트의 기본 프레임 버퍼는 8KB다.** 32KB 메시지에서 클라이언트가 먼저 1009(TOO_BIG)로
   끊는다. 하네스에서 1MB로 올렸다. 브라우저에는 해당 없는 제약이다.
3. **실제 채팅 경로(`/app/chat.sendText`)는 태우지 못했다.** CONNECT 인증(§2)이 없어 `@AuthenticationPrincipal`이
   null이고, 채팅방 생성 API(#188)도 없다. 대신 `SimpMessagingTemplate`로 토픽에 직접 브로드캐스트해서
   **브로커·세션 계층만** 측정했다. 서비스 계층(DB 저장 포함) 부하는 2차 측정으로 남는다.
