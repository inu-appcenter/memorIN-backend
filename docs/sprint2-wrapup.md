## 3. 캘린더 뷰 — 날짜 조회 경로 신설 (해결)

스프린트 문서에는 완료로 체크돼 있었으나, 게시물 조회 API에 **날짜로 범위를 좁히는 파라미터가 없었다.**
`PostRepository.findUserFeed`는 `recorded_date DESC, id DESC` 정렬과 키셋 페이징만 하고 날짜로 거르지 않았다.

전체 피드를 받아 클라이언트에서 거르는 방식은 **커서 페이지네이션과 충돌한다** — 탭한 날짜의 게시물이
뒤쪽 페이지에 있으면 화면에 아예 나타나지 않는다. 그래서 서버에서 좁히는 쪽으로 처리했다.

```http
GET /api/posts?userId={uuid}&from=2026-08-01&to=2026-08-31   # 월 범위
GET /api/posts?userId={uuid}&from=2026-08-11&to=2026-08-11   # 날짜 하나 탭
```

- `from`/`to`는 `recorded_date` 기준, 경계 포함, `yyyy-MM-dd`. 둘 다 생략하면 기존과 동일하다.
- `from > to`는 400(`COMMON_002`), 날짜 형식 오류도 400이다.
- **인덱스 추가 없음** — `idx_posts_user_id (user_id, recorded_date DESC, id DESC)`의 두 번째 컬럼이
  `recorded_date`라 `user_id`로 좁힌 뒤 범위 스캔이 그대로 인덱스를 탄다.

`PostDateRangeFilterTest`가 경계 포함·단일 날짜·한쪽만 지정을 검증하고, **범위 안에서 커서로 끝까지
넘겨도 범위 밖 게시물이 섞이지 않는 것**까지 고정한다.

## 4. 이번 정리에서 처리한 것 — main → develop 역머지

`develop`에 추천 피드 수정이 빠져 있었다.

#118(추천 피드 전면 500) 수정 PR #129가 `develop`이 아니라 **`main`에 직접 머지**되면서 두 브랜치가 갈라졌다.

| 브랜치 | `PostRepository.findRecommendationCandidates` |
| --- | --- |
| `main` | `AND p.created_at <= :asOf` — 정상 |
| `develop` (역머지 전) | `AND p.created_at <= : asOf` — 콜론 뒤 공백, `PSQLException` |

유일한 회귀 테스트 `RecommendedFeedQueryTest`도 `main`에만 있어 **`develop` CI가 이 결함을 잡을 수 없는 상태**였다. 머지 방향이 `develop → main` 한쪽뿐이라 시간이 지나도 자동으로 해소되지 않는다.

**이 PR에서 `main`을 `develop`으로 역머지해 해소한다.** (fast-forward, 충돌 없음)

> **교훈**: 핫픽스를 `main`에 직접 머지하면 `develop`은 영원히 고쳐지지 않는다.
> 긴급 수정이 `main`으로 갔다면 같은 날 역머지한다.

## 5-1. 결산 이후 추가로 드러난 것

이 문서를 쓰는 과정에서 **머지된 신규 API 네 개가 전부 동작한 적이 없었다**는 것이 확인됐다.

| API | 원인 | 처리 |
| --- | --- | --- |
| 추천 피드 | 네이티브 쿼리 `: asOf` (콜론 뒤 공백) | #118 → 역머지로 `develop` 반영 |
| 이모지 | 엔티티 `comment_emoji` vs DDL `emoji` + `NAMED_ENUM` 누락 | #152에서 수정 |
| 친구 피드 | JPQL 인라인 enum 리터럴 → `type "follow_state" does not exist` | #151에서 수정 |
| **댓글 삭제** | `softDelete()`가 `body=null`인데 컬럼이 `TEXT NOT NULL` | **8절에서 수정** (V5) |

친구 피드 장애는 #139(쿼리 카운트 테스트)를 작성하다 발견했다.
댓글 삭제 장애도 마찬가지로 **삭제 경로를 처음 실행하는 테스트를 짜자 그제서야 드러났다.**

넷 다 코드 리뷰로는 잡히지 않는다 — 콜론 뒤 공백, 캐스팅 타입명, 테이블명, NOT NULL 제약은
전부 실행해야 보인다. 그리고 넷 다 **그 경로를 실행하는 테스트가 하나도 없었다.**

댓글 삭제는 특히 뼈아프다. 엔드포인트가 있다는 이유로 이 문서 1절에서 **"✅ 완료"로 판정했던 항목**이다.
매핑 존재 여부로 게이트를 판정하면 이런 걸 놓친다.

> **제안**: 새 API를 머지할 때 그 경로를 한 번이라도 실행하는 테스트 1개를 요구한다.
> 완벽한 커버리지가 아니라 "한 번은 돌려봤다"는 최소선이다. 패턴은 `docs/n+1-audit.md` §3-2.
> 게이트 판정도 엔드포인트 존재가 아니라 **그 경로를 실행하는 테스트**로 한다.

### 공개범위 — 판정은 원래 어긋나 있지 않았다

이 문서 1절은 처음에 "목록과 단건의 친구 판정 기준이 달라 검증 불가"라고 적었는데, **사실이 아니었다.**

- 목록 `findUserFeed`: SQL 안에서 `(follower=나 AND following=작성자) OR (following=나 AND follower=작성자)` → 양방향
- 단건 `PostAccessPolicy.assertReadable`: `friend1 || friend2` → 양방향

둘은 같은 조건이고, 단건·댓글·좋아요·미디어 다운로드가 전부 `assertReadable` 하나를 호출한다.
`#141`이 지적한 `PostService.isFriend`는 **호출부가 하나도 없는 죽은 메서드**였다.
그래서 #141은 로직 통합이 아니라 데드코드 제거로 끝났다.

문제는 **판정이 갈라졌는지 확인할 방법이 없었다는 것**이다. `PostVisibilityFilterTest`가 그 자리를 메운다.
개수만 세지 않고 마지막에 **"목록에 나온 게시물은 단건 조회도 열린다"**를 교차 검증하므로,
한쪽만 고쳐서 판정이 갈라지면 그 시점에 깨진다.

> 친구 피드(`findFriendFeed`)는 `findFollowingIds` 기반 **단방향**이라 위 둘과 다르다.
> 다만 이건 "팔로잉 기반"이라는 의도된 동작이고, 게이트도 Sprint 3("친구 피드 팔로잉만 노출")이다.

### 댓글 스레드 — HTTP N+1과 SQL N+1을 함께 막았다

응답에 이모지 집계가 없어 FE가 댓글 N개마다 `GET /api/comments/{id}/emojis`를 N번 호출해야 했다(HTTP N+1).
배치 집계 쿼리 `CommentEmojiRepository.countByCommentIds`는 이미 있었으므로 스레드 조회에서 한 번 부르게 했다.

작성자 닉네임을 추가하면서 새 위험이 생긴다 — 기존에는 `getUser().getId()`(PK)만 읽어 프록시가
초기화되지 않았지만, 닉네임을 읽는 순간 댓글 1건당 SELECT 1번이 된다.
`findThreadByPostId`에 `JOIN FETCH c.user`를 걸고 `CommentThreadQueryCountTest`로 고정했다.

**댓글 수와 무관하게 SQL 3개**(게시물 1 + 스레드 1 + 이모지 집계 1)다. 테스트가 이 숫자를 직접 검증한다.
