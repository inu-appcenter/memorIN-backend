## 3. 게이트 차단 ① — PR #169 (게시물 공유 API)

8/18에 올라온 뒤 **리뷰어가 붙지 않은 채 이틀**이 지났다. 지금 상태로 머지하면 **애플리케이션이 기동하지 않는다.**

| 심각도 | 항목 | 내용 |
|---|---|---|
| 🔴 차단 | Flyway 버전 충돌 | develop에 이미 `V7__add_notification_history.sql`(#168)이 있는데 PR이 `V7__change_column_message_entity.sql`을 추가한다. 같은 버전 두 개면 기동 시 실패한다 → **V8로 변경** |
| 🔴 차단 | 적용된 마이그레이션 수정 | `V1__init.sql`을 고쳤다. 이미 V1을 적용한 DB에서는 체크섬 불일치로 마이그레이션이 멈춘다 → V1 복원 후 변경분은 새 파일로 |
| 🔴 결함 | 발신자 식별 | `UUID.fromString(userDetails.getUsername())` — `getUsername()`은 **닉네임**을 반환한다(`UserDetailsImpl`). UUID 파싱이 항상 실패한다 → 다른 컨트롤러와 같이 `getUserId()` |
| 🔴 결함 | WebSocket 인증 부재 | `/ws/**`가 permitAll이고 CONNECT 검증이 없어 `@AuthenticationPrincipal`이 `null`이다. 누구나 연결·구독할 수 있다 → `docs/sprint4-architecture-review.md` §2 |
| 🟠 결함 | 리포지토리 타입 | `ChatRoomsRepository extends CrudRepository<ChatRooms, Long>` + `Optional<Object> findById(UUID)` + 호출부 `(ChatRooms)` 캐스팅. ID 타입이 틀렸다 → `JpaRepository<ChatRooms, UUID>` |
| 🟠 게이트 | 테스트 없음 | +301/-2줄에 테스트 파일 0개. 게이트 문구가 "통합 테스트"다 |

## 4. 알림 — 조회는 되는데 데이터가 생기지 않는다

`NotificationService.save(...)`는 완성돼 있으나 **`notifications` 패키지 밖에서 호출하는 코드가 하나도 없다.**

```
[발생 지점]        [저장]                      [발송]
팔로우 요청   →   NotificationService.save()  →  FCM / Web Push
팔로우 수락        ← 호출부 0개 (구멍)            ← Sprint 4
댓글 작성
```

`GET /api/notifications`는 정상 동작하지만 언제나 `items: []`다.
게이트를 **데모로** 확인하려면 발생 지점 연결이 선행돼야 한다.

- 연결 방식(서비스 직접 호출 vs 스프링 이벤트 + `AFTER_COMMIT`)은 `docs/sprint4-architecture-review.md` §9에 정리했다.
- 팔로우가 롤백됐는데 알림만 남는 상황을 막아야 하므로 **이벤트 + 커밋 후 처리**를 권한다.
- `NotificationType.LIKE`는 폐기된 게시물 좋아요에서 온 값이라 쓰이지 않는다(#148 정리 대상).

## 5. 게이트 차단 ② — 받은 팔로우 요청 거절 (#163)

원인을 코드에서 확인했다.

- 목록(`GET /api/follows/requests`)은 **받은** 요청, 즉 `(follower = 상대, following = 나)` 행을 반환한다.
- 거절(`DELETE /api/follows/{followingId}`)은 `findByFollowerIdAndFollowingId(follower = 나, following = path)`
  로 **반대 방향**을 찾는다. 행이 없으니 **항상 404 `FOLLOW_001`** 이다.

파라미터 의미도 어긋나 있다 — 수락은 `followId`(팔로우 행 id)를 받는데 거절은 `followingId`(사용자 id)를 받는다.
목록 응답이 `followId`를 내려주므로 **`DELETE /api/follows/{followId}`로 맞추는 쪽**이 자연스럽다.

같은 PR(#162)에서 나온 나머지 두 건도 미해결이다.

| 이슈 | 내용 | 게이트 영향 |
|---|---|---|
| #163 | 받은 요청 거절 항상 실패 | **직접 차단** |
| #164 | 탈퇴 유저 프로필이 그대로 조회됨 | 간접 (검색은 #166에서 `deleted_at` 필터를 넣었는데 이 API만 빠졌다) |
| #165 | 응답 봉투 미적용 + 이미지 키 그대로 노출 | 간접 (FE 연동) |

## 6. 미착수 — 태그/메타데이터 탐색 API

건희님의 Sprint 3 두 번째 태스크다. **코드도 이슈도 없다.**

선행 조건도 아직 열려 있다: `content` JSONB에서 **태그가 어느 키에 들어가는지** 합의되지 않았다
(Sprint 2 결산 §7에서 넘어온 항목). `@ValidJson`은 "유효한 JSON"인지만 보고 구조는 검증하지 않으며,
Sprint 2에서 사용되지 않던 GIN 인덱스를 제거했으므로 재도입 여부도 함께 정해야 한다.

→ Sprint 4로 이월할지, 범위에서 뺄지 **플래닝에서 결정 필요.**

## 9. 결론

**Sprint 3은 게이트 4개 중 1개 충족 상태로 리뷰에 들어간다.**

막는 것은 두 개다.

1. **PR #169** — 리뷰가 붙지 않아 이틀 정체. 기동 실패 사유 2건 포함(§3)
2. **#163** — 소셜 탐색 흐름의 마지막 한 칸(§5)

둘 다 원인이 특정돼 있어 **재작업이 아니라 수정**으로 닫을 수 있다.
알림(§4)은 조회 API가 완성된 만큼 발생 지점만 연결하면 되고, 이는 Sprint 4 FCM 태스크의 선행 조건이기도 하다.

Sprint 4는 성격이 다른 스프린트다 — 연결이 유지되는 동안 서버가 상태를 들고 있는다.
착수 전 결정 사항은 `docs/sprint4-architecture-review.md`에 정리했고, 그 체크리스트(§10)를 플래닝 안건으로 쓴다.
