## 4. 리뷰 이후 새로 드러난 것

W10 코드 리뷰가 잡지 못한 것들이다. 셋 다 **코드를 읽어서는 보이지 않고 배선을 따라가야** 보인다.

### 4-1. 푸시를 배포 환경에서 켤 수 없었다

`application-docker.properties`가 읽는 환경변수 6개(`FIREBASE_ENABLED` · `FIREBASE_SERVICE_ACCOUNT_PATH` ·
`WEB_PUSH_ENABLED` · `WEB_PUSH_VAPID_PUBLIC_KEY` · `WEB_PUSH_VAPID_PRIVATE_KEY` · `WEB_PUSH_VAPID_SUBJECT`)가
`docker-compose.yml`에도 `.env.example`에도 **하나도 없었다.**

기본값이 `false`라 컨테이너는 **푸시가 꺼진 채로 조용히 뜬다.** 에러도 로그도 없다.
발송 코드를 다 만들고 통합 테스트까지 붙였는데 켤 방법이 없었다.

서비스 계정 JSON 경로도 틀려 있었다. `FirebaseConfig`가 `FileInputStream`으로 읽는데 README는
`src/main/resources`를 안내하고 있었다 — `bootJar`로 구우면 JAR 안으로 들어가 읽히지 않는다.

→ PR [#237](https://github.com/inu-appcenter/memorIN-backend/pull/237). `secrets/` 디렉터리 볼륨 마운트로 바꿨다.

**#156(CORS 전달 누락) · #158(.env.example 불일치)과 같은 종류의 재발이다.** 이번이 세 번째다.

### 4-2. 채팅 메시지는 푸시로 넘어가지 않는다

`NotificationService.save(...)` 호출부는 `FollowService` 2곳 + `PostCommentService` 1곳뿐이다.
`MessageService`는 알림을 전혀 부르지 않는다.

README의 핵심 기능인 **"미접속 상태면 FCM / Web Push 알림으로 전환"이 채팅에는 연결돼 있지 않다.**
Sprint 4 태스크 목록에도 이 연결이 없었다 — 발송 기능만 있고 발생 지점이 빠졌다.

→ #216. `NotificationType.MESSAGE` 추가가 선행이다.

### 4-3. 구독 인가는 구독 시점만 검사한다

#209가 SUBSCRIBE 인가를 넣었지만 **이미 맺어진 구독은 강퇴·나가기 뒤에도 살아 있다.**
발신은 막히는데 수신만 남아, 강퇴당한 사람이 탭을 닫을 때까지 그 방 대화를 계속 받는다.

→ #210 · PR [#240](https://github.com/inu-appcenter/memorIN-backend/pull/240). 배달 시점 필터로 처리했다.

## 5. 릴리스 상태 — 세 번째 사고를 막았다

Sprint 4 마감 시점(#208, 09-08) 이후 `develop`이 `main`보다 **12커밋 앞서 있었다.**
그 안에 들어 있던 것이 하필 이랬다.

| 미릴리스 항목 | `main`에서의 증상 |
|---|---|
| #209 STOMP 연결·구독 인가 | 토큰 없이 연결해 `roomId`만 알면 **남의 채팅방 대화를 실시간으로 전부 수신** |
| #213 Web Push BouncyCastle | `WEB_PUSH_ENABLED=true`로 켜면 **기동 실패** |

앞의 것은 보안 결함, 뒤의 것은 기동 차단이다. **Sprint 5의 오픈소스 배포 대상이 `main`이므로
이 상태로 공개하면 그대로 나간다.**

Sprint 2에 같은 일이 있었다(#157 — 마감 릴리스 누락으로 댓글 삭제·이모지가 운영에서 실패).
`docs/sprint3-wrapup.md` §8이 "게이트 처리 후 릴리스 PR을 올린다"로 정리해 둔 절차를 이번에 적용했다.

→ [#235](https://github.com/inu-appcenter/memorIN-backend/pull/235) 머지 완료 (2026-09-14). 현재 `main` = `develop`.

> **교훈**: 스프린트 마감 릴리스를 "나중에"로 미루면 다음 스프린트가 시작되고도 남는다.

## 8. 한 줄 요약

**Sprint 4는 게이트 8개 중 5개 충족 · 3개 절반으로 닫는다.**

W10 리뷰 시점의 "서 있는 게이트 1개"에서 여기까지 온 것은 차단 항목 두 개(principal 타입,
CONNECT 인증)를 풀었기 때문이고, 남은 절반 셋 중 둘은 **기능이 아니라 배선**(환경변수·트리거) 문제다.

되짚을 것 하나. 이번 스프린트에서 실제로 데모를 막았던 결함 셋(#207 principal, #209 인증 부재,
#214 환경변수)은 **전부 "코드는 있는데 연결이 안 된" 종류**였다. 단위 테스트로는 전부 통과하고,
코드 리뷰로도 두 개는 놓쳤다. 실행 경로를 한 번 태워 보는 테스트(#204)와 배선을 확인하는 절차가
같이 가야 한다.

Sprint 5는 이것을 밖에서 검증할 기회이기도 하다 — 배포 게이트의 "`git clone` → `.env` → `docker compose up`"이
정확히 **배선을 처음부터 따라가는 절차**다.
